PURPOSE
=======

This is a recommendation backlog, not a claim that every item should be built.
The order favors trust, data safety, predictable runtime behavior, and features
that deepen Emora's existing companion experience without turning normal chat
into a crowded dashboard.

SECTION 1 - PRODUCTION STABILITY AND DATA SAFETY
================================================

S01 - SINGLE-DELIVERY BACKGROUND JOBS [P0, M]

Problem:
The scheduled check-in loop starts inside every FastAPI process. Running two
Uvicorn workers or multiple instances can send the same check-in more than once.

Recommendation:
- Move scheduled delivery to one dedicated worker, or guard each job with a
  MongoDB/Redis lease containing owner, acquired_at, and expires_at.
- Make each delivery idempotent with a unique user_id + local_date + channel key.
- Retry transient email failures with bounded exponential backoff and jitter.
- Record attempted, delivered, failed, skipped, and unsubscribed outcomes.

Done when:
Two API workers can run for a full schedule window and exactly one message is
delivered per eligible user.


S02 - DURABLE CHAT TURN STATE MACHINE [P0, L]

Problem:
A user message and AI reply are assembled in memory and the conversation is
replaced after generation. A crash, timeout, duplicate browser submit, or two
simultaneous tabs can lose a turn, duplicate a turn, or overwrite newer data.

Recommendation:
- Accept an idempotency key/client_turn_id for every send.
- Persist the user turn first with state=queued/generating.
- Generate outside the database critical section.
- Atomically finalize the matching turn with state=complete or state=failed.
- Use conversation version checks and $push/$set updates instead of replacing
  the whole conversation document.
- Provide Retry and Cancel without resending the user's message.

Done when:
Repeated identical requests, process interruption, and concurrent tabs cannot
lose or duplicate a completed turn.


S03 - ASYNC DATABASE BOUNDARY [P0, L]

Problem:
Most routes are async-capable, but synchronous PyMongo operations can block the
event loop during slow database calls, including chat and live room activity.

Recommendation:
- Adopt PyMongo's supported async API or isolate all blocking database work in a
  bounded executor.
- Add explicit connect, read, and write timeouts.
- Keep one documented database access boundary rather than mixing patterns.
- Load-test chat, Focus Together SSE, and account export while MongoDB is slow.

Done when:
A deliberately slow database request does not freeze unrelated health, SSE, or
static/API requests.


S04 - REAL READINESS AND DEPENDENCY HEALTH [P0, S]

Recommendation:
- Return HTTP 503 from /health/ready when required dependencies are unavailable;
  do not only return a JSON field saying degraded with HTTP 200.
- Separate required components from optional ones such as email, web search,
  camera, and voice.
- Include bounded checks for MongoDB, Redis when required, model/provider state,
  storage writeability, and background-worker lease health.
- Keep /health lightweight and content-free.


S05 - CONFIGURATION VALIDATION [P0, M]

Recommendation:
- Validate environment settings once at startup with clear field-level errors.
- Reject malformed integers, negative queue sizes, invalid URLs, unsafe public
  callback URLs, and conflicting provider flags.
- Fail closed in production when trusted proxies, CORS/origins, storage paths,
  or required services are not configured.
- Print a sanitized startup summary that never includes secrets.


S06 - DATABASE MIGRATION AND SCHEMA VERSIONING [P0, M]

Recommendation:
- Add numbered, repeatable migrations for indexes and document-shape changes.
- Record the applied migration version in MongoDB.
- Make migrations safe to resume after interruption.
- Add forward/backward compatibility for at least one deployed version during
  rolling releases.
- Test migrations against a copy of realistic older data.


S07 - BACKUP, RESTORE, AND DISASTER-RECOVERY DRILLS [P0, M]

Recommendation:
- Automate encrypted MongoDB backups with retention tiers.
- Back up required user-uploaded files consistently with their database records.
- Perform scheduled restore drills into an isolated database.
- Document recovery time objective (RTO) and recovery point objective (RPO).
- Verify that account deletion propagates to backups according to the published
  retention policy.


S08 - RETENTION AND ORPHAN CLEANUP [P0, M]

Recommendation:
- Define retention for auth sessions, security events, OTP fields, billing
  requests, generated audio, abandoned attachments, ended focus rooms, presence,
  web-search cache, and failed generation records.
- Add TTL indexes where MongoDB cleanup is appropriate.
- Add a safe reconciliation job for database rows whose files are missing and
  files that have no database owner.
- Expose retention rules in the privacy UI and account export.


S09 - ATOMIC DISTRIBUTED RATE LIMITING [P0, M]

Problem:
The Redis limiter counts and inserts in separate operations, which allows races.
The in-process fallback can accumulate identity buckets for a long-running app.

Recommendation:
- Use one Lua script or transaction for prune + count + insert + expiry.
- Return an accurate Retry-After value.
- Periodically evict empty/old in-memory buckets.
- Define fail-open versus fail-closed behavior per route class.
- Add limits for exports, restore commits, account deletion, expensive insights,
  and room creation in addition to inference/auth endpoints.


S10 - TRUSTED PROXY AND CLIENT-IP HANDLING [P0, S]

Recommendation:
- Honor X-Forwarded-For and X-Forwarded-Proto only from configured trusted
  proxies.
- Prefer the reverse proxy's canonical real-IP header configuration.
- Test that a direct client cannot spoof HTTPS detection or obtain another rate
  limit identity through arbitrary forwarded headers.


S11 - GRACEFUL SHUTDOWN AND QUEUE DRAINING [P1, M]

- Stop admitting new chat/TTS jobs during shutdown.
- Give active jobs a bounded grace period, then mark unfinished turns retryable.
- Close MongoDB/Redis/HTTP clients and SSE streams explicitly.
- Ensure model loading cannot continue after application shutdown starts.


S12 - CIRCUIT BREAKERS AND RETRY BUDGETS [P1, M]

- Add per-provider circuit breakers for web search, SMTP, local/cloud inference,
  Redis, and voice fallback.
- Retry only idempotent operations and use jittered backoff.
- Show a useful degraded-mode message without inventing an AI answer.
- Record provider state transitions without storing prompts or responses.


S13 - LARGE-CONVERSATION STORAGE STRATEGY [P1, L]

Problem:
Embedding an ever-growing messages array in one MongoDB conversation document
will eventually make reads, replacements, exports, and the document-size limit
problematic.

Recommendation:
- Store turns in a separate conversation_messages collection.
- Index conversation_id + sequence and paginate older messages.
- Keep a compact conversation summary and recent-window cache.
- Migrate existing embedded messages without breaking saved links.


S14 - SAFE, STREAMING ACCOUNT EXPORTS [P1, M]

- Stream large exports instead of loading every record into memory.
- Include all user-owned domains with an explicit manifest and schema version.
- Optionally include attachment bytes in an encrypted archive.
- Create export jobs with expiry for large accounts.
- Add export/restore compatibility tests across versions.


S15 - CONSISTENT DELETE WORKFLOWS [P1, M]

- Use a deletion job/saga with a durable checklist for Mongo collections, files,
  sessions, rooms, billing metadata, caches, and derived records.
- Make retries safe and visible to the user.
- Add a final reconciliation report without retaining deleted content.


S16 - RESOURCE QUOTAS [P1, M]

- Enforce per-user and global limits for stored attachment bytes, conversation
  count, export frequency, saved research, memories, room messages, and audio.
- Return usage and remaining quota from server-owned access metadata.
- Never enforce critical limits only in JavaScript.

SECTION 3 - SECURITY AND PRIVACY HARDENING
==========================================

SEC01 - MOVE AUTH TOKENS OUT OF LOCALSTORAGE [P1, L]

Current browser bearer tokens are accessible to JavaScript. A successful XSS can
therefore steal a long-lived session.

Recommendation:
- Prefer Secure, HttpOnly, SameSite session cookies.
- Add CSRF protection to state-changing requests.
- Rotate refresh tokens and keep access tokens short-lived.
- Preserve session listing/revocation and multi-device behavior.
- If bearer storage must remain temporarily, shorten expiry and strengthen CSP.


SEC02 - STRICT CONTENT SECURITY POLICY [P1, M]

- Inventory scripts, styles, fonts, model assets, workers, media, and connections.
- Remove inline executable code where practical or use per-response nonces.
- Deploy CSP in report-only mode, fix violations, then enforce it.
- Add object-src 'none', base-uri 'self', frame-ancestors 'none', and narrow
  connect-src/media-src/img-src directives.


SEC03 - XSS-SAFE DOM CONSTRUCTION [P1, M]

- Audit every innerHTML/insertAdjacentHTML site that includes server/user data.
- Prefer textContent and DOM element construction.
- Keep one well-tested escaping utility for the small number of HTML templates
  that remain.
- Add payload tests for text, attributes, URLs, SVG, malformed Unicode, and
  stored community/chat/research content.


SEC04 - MULTI-FACTOR AUTHENTICATION AND PASSKEYS [P2, L]

- Add passkeys/WebAuthn as the preferred strong login option.
- Offer TOTP with recovery codes for users who need it.
- Require recent authentication for password, email, MFA, export, restore,
  session-revocation, billing, and account-deletion actions.


SEC05 - EMAIL OWNERSHIP AND ACCOUNT-LINKING RULES [P1, M]

- Store email_verified_at and make verification state explicit.
- Define safe linking behavior when Google and local accounts use the same email.
- Notify users about new sign-ins, password changes, linked providers, export,
  and account deletion.
- Add recovery paths that do not reveal whether an email exists.


SEC06 - UPLOAD PIPELINE HARDENING [P1, L]

- Replace large base64 JSON uploads with bounded multipart streaming.
- Validate extension, declared MIME type, magic bytes, decoded dimensions, and
  decompression ratio.
- Store uploads outside the public static tree when authorization is required.
- Quarantine until malware scanning completes.
- Generate server-owned filenames and prevent active HTML/SVG execution.


SEC07 - ADMIN SAFETY [P1, M]

- Remove production owner identities from code defaults; require deployment
  configuration.
- Require strong authentication and recent re-auth for subscription changes.
- Record immutable audit entries with actor, target, before/after state, reason,
  request ID, and time.
- Add pagination and least-privilege admin roles.


SEC08 - PRIVACY THREAT MODEL [P1, M]

Document data flows and threats for chat, memory, camera, voice, web search,
community, focus rooms, backups, exports, and third-party providers. For every
data type record purpose, storage, retention, access, deletion, and whether it
leaves the device. Revisit the model before each new integration.


SEC09 - FIELD-LEVEL PROTECTION FOR HIGH-SENSITIVITY DATA [P2, L]

Evaluate application-level encryption for journal content, explicit memories,
conversation content, and exports. Keep keys outside MongoDB, support rotation,
and understand that encryption can limit server-side search and analytics.


SEC10 - SAFETY RESPONSE LAYER [P1, M]

- Keep Emora explicitly non-clinical.
- Add deterministic handling for credible self-harm or immediate-danger language
  that encourages contacting local emergency/crisis and trusted human support.
- Do not diagnose, score risk publicly, contact others, or silently escalate.
- Localize resources by user-selected region and test false positives carefully.


SECTION 4 - AI QUALITY AND COMPANION INTELLIGENCE
================================================

F01 - STREAMING CHAT WITH CANCEL AND RESUME [P1, L]

- Stream tokens/events end to end instead of waiting for the entire response.
- Support Cancel while preserving the user turn and any safe partial response.
- Persist the final authoritative text once, with idempotent reconnect recovery.
- Emit separate private events for status, citations, and avatar behavior rather
  than exposing reasoning or Companion Brain JSON in text.


F02 - EDIT, RETRY, AND BRANCH A CONVERSATION [P1, L]

- Let users edit their most recent message, regenerate an answer, and branch from
  any earlier turn without destroying the original path.
- Show branches quietly in conversation history, not as clutter in normal chat.
- Keep memory extraction and feedback attached to the correct branch/version.


F03 - MEMORY INBOX AND EXPLANATIONS [P1, M]

- Add a review inbox for newly inferred memory candidates before long-term save,
  or provide an Undo window depending on the user's preference.
- Show source conversation, reason remembered, confidence, last used, expiry, and
  which answer used a memory.
- Support Always remember, Never remember this kind, Correct, Merge, and Expire.


F04 - MEMORY CONFLICT RESOLUTION [P1, M]

- Detect likely contradictions such as changed city, job, preference, or goal.
- Ask a neutral clarification instead of silently replacing facts.
- Keep bounded provenance and allow the user to choose current, historical, or
  delete both.


F05 - CONVERSATION SUMMARIES WITH USER CONTROL [P1, M]

- Create compact summaries for long conversations to reduce prompt size.
- Keep summaries factual, versioned, and editable/deletable.
- Never treat a generated summary as more authoritative than the user's current
  profile or explicit memory.
- Measure factual retention against a regression set.


F06 - PERSONAL AI QUALITY EVALUATION SUITE [P1, M]

Build a repository-owned evaluation set covering:
- Warm but not overdramatic responses.
- Correct use and non-use of memory.
- No invented personal facts.
- No private reasoning/schema leakage.
- Emotional follow-ups that stay local instead of triggering web search.
- Current questions that do use web grounding and cite supported claims.
- Safety boundaries, refusal quality, and response brevity.
- Character consistency without dependence or manipulation.

Run it against model/config changes and compare quality plus latency.


F07 - SOURCE-AWARE RESEARCH MODE [P1, L]

- Keep ordinary companion chat calm and local-first.
- Add an explicit research mode for multi-query web work, source cards, dates,
  claim-level citations, conflicting-source notes, and Save to Research Shelf.
- Let users inspect the exact search queries before/after execution.
- Treat web content as untrusted data and prevent prompt injection from sources.


F08 - BETTER RESPONSE FEEDBACK LOOP [P1, M]

- Expand feedback beyond one reason: too long, too clinical, forgot context,
  incorrect fact, unwanted search, wrong tone, repetitive, or unsafe.
- Let the user optionally provide a preferred rewrite.
- Use aggregate feedback for evals and settings suggestions, never silent
  personality changes.


F09 - USER-SELECTED LANGUAGE AND MULTILINGUAL MEMORY [P2, L]

- Add explicit language preference and per-conversation language choice.
- Preserve names and code-switching in memory/search.
- Verify the selected text and voice models for each supported language.
- Localize safety resources, dates, time zones, and email templates.


F10 - VOICE CONVERSATION TURN-TAKING [P2, XL]

- Add real streaming speech recognition, endpointing, barge-in, interruption,
  partial transcript correction, and low-latency TTS playback.
- Keep microphone use explicit and visually obvious.
- Make text chat fully usable when speech APIs or device audio fail.
- Verify with real devices; mocks cannot prove audible output or turn-taking.


F11 - PERSONAL PRONUNCIATION AND NAME GUIDE [P2, M]

Allow users to teach pronunciations for their name and important people/places,
preview them locally, and delete them. Store phonetic guidance separately from
the displayed text and never infer sensitive identity attributes.


F12 - MODEL DOWNLOAD AND DEVICE CAPABILITY CENTER [P2, M]

- Show model installed/downloading/loading/ready/failed status.
- Estimate required disk and unified memory before download.
- Allow retry, verified cleanup, and selection only among supported models.
- Provide a low-resource mode that disables camera/voice before destabilizing
  normal text chat.


SECTION 5 - USER-FACING PRODUCT FEATURES
========================================

F13 - NOTIFICATION CENTER [P1, M]

Create a server-owned inbox for check-ins, goal reminders, security alerts,
weekly-story readiness, export completion, and room invitations. Include read,
dismiss, mute category, quiet hours, and expiry. Do not rely on ephemeral toasts.


F14 - WEEKLY REVIEW WORKFLOW [P1, M]

Turn existing real insights, goals, journal entries, Moments, and check-ins into
an optional user-led weekly review:
- What felt meaningful?
- What changed?
- What should Emora remember or forget?
- Which goal gets one tiny next step?

Save only the choices the user confirms.


F15 - GOAL STEPS, SCHEDULES, AND REFLECTIONS [P1, M]

- Add ordered substeps, optional due dates, recurring cadence, pause/archive,
  and completion reflection.
- Keep language gentle and avoid punitive streaks.
- Let Emora propose a tiny step, but require user confirmation before saving.


F16 - CALENDAR AND TASK INTEGRATION [P2, L]

- Begin with one provider and explicit read/write scopes.
- Show a confirmation screen before creating, editing, or deleting anything.
- Store external IDs and sync cursors, not unnecessary event content.
- Make disconnection and data removal obvious.
- Never imply reminders are reliable until background delivery is production
  hardened.


F17 - PERSONAL DOCUMENT LIBRARY [P2, XL]

Allow opt-in PDF/TXT/DOCX uploads for conversation-grounded questions:
- Parse deterministically and show extracted text/source page references.
- Chunk and index per user with deletion and re-index controls.
- Cite document title/page in answers.
- Defend against prompt injection inside documents.
- Keep this separate from ordinary small chat attachments.


F18 - SEMANTIC SEARCH WITH A PRIVATE INDEX [P2, L]

Enhance universal search across conversation turns, journal entries, memories,
Moments, goals, and research notes. Keep indexes user-scoped, support exact/date
filters, explain why results matched, and rebuild/delete the index on demand.


F19 - OFFLINE-SAFE DRAFTS AND PWA SHELL [P2, L]

- Make the app installable and keep navigation/static assets available offline.
- Queue only explicit draft saves, never pretend AI replies or server writes
  succeeded while offline.
- Encrypt or minimize sensitive local drafts and provide Clear this device.
- Reconcile drafts after reconnect with conflict-aware prompts.


F20 - ACCESSIBILITY PROGRAM [P1, M]

- Target WCAG 2.2 AA for keyboard access, focus order, labels, error summaries,
  contrast, reflow, zoom, reduced motion, and screen-reader announcements.
- Provide avatar motion intensity, autoplay voice, transcript, font size, and
  high-contrast controls.
- Run automated checks plus keyboard and screen-reader QA on every core route.


F21 - FOCUS TOGETHER QUALITY-OF-LIFE [P2, M]

Build on the current authoritative SSE room contract:
- Host-configured focus/break cycles.
- Ready state and gentle shared milestones.
- Reconnect indicator and explicit ended-room summary.
- Optional post-room private reflection saved only to each user's account.
- Abuse report/block controls that preserve anonymous identities.

Do not reintroduce polling or persistent shared transcripts after room end.


F22 - COMMUNITY SAFETY AND DISCOVERY [P2, L]

- Add topic tags, sort/filter, saved posts, block/mute, moderation queue, appeal,
  and rate/velocity abuse detection.
- Keep identity anonymous to other users while retaining server-side abuse
  controls.
- Publish clear community rules and moderation outcomes.


F23 - SUBSCRIPTION SELF-SERVICE AFTER REAL BILLING [P2, L]

Only after connecting a real billing provider:
- Hosted checkout/customer portal and signed webhook verification.
- Idempotent subscription event processing.
- Trial, renewal, invoice, cancellation, grace period, and refund state handling.
- Clear downgrade behavior that retains data but enforces access.
- Reconciliation between provider state and server entitlements.

Until then, keep the current checkout explicitly labeled as a preview/request and
never collect or persist payment credentials.


F24 - COMPANION RELATIONSHIP CONTROLS [P2, M]

Let users explicitly choose:
- How proactive Emora may be.
- Preferred response length and directness.
- Whether to celebrate streaks/milestones.
- Topics Emora should not raise unprompted.
- Memory strictness and automatic expiry.

Display all active controls in one understandable page and make Reset to defaults
safe and reversible.


F25 - DATA TIMELINE AND CORRECTION CENTER [P2, L]

Provide a chronological, filterable view of what Emora stored or derived:
check-ins, memories, Moments, goals, behavior reports, feedback, and searches.
Users should be able to correct/delete source data and see which derived views
will change.


F26 - IMPORTERS WITH EXPLICIT MAPPING [P3, L]

Support carefully scoped imports from exported notes/chat/journal formats. Always
preview counts and examples, map fields explicitly, detect duplicates, and make
the import reversible for a limited window.


F27 - NATIVE MOBILE COMPANION [P3, XL]

Consider only after the web API contracts, background jobs, token security,
notifications, and offline conflict rules are stable. Start with a thin client
that preserves server ownership rather than duplicating business logic.


SECTION 6 - PERFORMANCE AND ARCHITECTURE CLEANUP
================================================

A01 - DOMAIN SERVICE BOUNDARIES [P1, L]

Several routers contain database queries, policy decisions, serialization, and
business workflows together. Gradually move logic into focused services for
chat turns, focus rooms, schedules, billing, account lifecycle, insights, and
experiences. Keep routes thin and preserve their public contracts.


A02 - REQUEST/RESPONSE SCHEMAS EVERYWHERE [P1, M]

Use explicit Pydantic response models for private APIs, with stable camelCase or
snake_case policy. This catches accidental exposure of Mongo fields and private
brain/analysis metadata. Version breaking response changes deliberately.


A03 - QUERY AND PAGINATION AUDIT [P1, M]

- Replace unbounded list conversions and full conversation scans.
- Use cursor pagination for messages, posts, search, memories, journal, goals,
  events, and admin users.
- Add indexes based on real explain plans and slow-query metrics.
- Cache only derived, non-sensitive results with clear invalidation.


A04 - FRONTEND MODULE AND DOM-SAFETY CLEANUP [P2, L]

- Break very large page scripts into small repository-owned ES modules.
- Centralize authenticated fetch, cancellation, retry, error mapping, escaping,
  date/time formatting, and state transitions.
- Keep the existing server-rendered/vanilla-JS architecture unless measured
  complexity justifies a framework migration.


A05 - STATIC ASSET DELIVERY [P2, M]

- Fingerprint assets in production and use immutable cache headers.
- Compress/minify first-party CSS and JS in a repeatable build step.
- Lazy-load VRM, camera, voice, and heavy room assets only on their routes.
- Add image dimensions, modern formats, and responsive variants.


A06 - MODEL RESOURCE COORDINATOR [P1, L]

Chat, vision, and TTS can compete for unified memory on Apple Silicon. Add one
resource coordinator that knows active models, job priority, memory budget, idle
unload policy, and low-memory fallback. Protect normal text chat from optional
camera/voice workloads.


A07 - CACHE CONTRACTS [P2, M]

Document ownership, key format, size limits, TTL, privacy level, invalidation,
and multi-process behavior for web search, provider health, audio, model state,
and dashboard-derived results. Avoid module-global caches that silently diverge
across workers.


A08 - API VERSIONING AND COMPATIBILITY [P2, M]

Before native clients or external integrations, define /api/v1 or an equivalent
versioning policy, deprecation headers, schema changelog, and compatibility tests.

FEATURES TO AVOID OR DELAY
==========================

1. Do not add VRM, preset prompts, companion cards, or insight panels back into
   normal Chat with Emora. Keep immersive behavior on the dedicated companion
   experience.

2. Do not implement autonomous messages, calendar writes, emails, or contacts
   without explicit consent, confirmation, auditability, and reliable jobs.

3. Do not claim therapy, diagnosis, medical monitoring, or crisis intervention.

4. Do not store camera frames, continuous video, face identity, demographics, or
   inferred medical conditions.

5. Do not activate paid access from client-side checkout success. Subscription
   state must come from verified server-side billing events or an administrator.

6. Do not add a larger local language model until benchmarked with chat, voice,
   and VRM active on the target machine. The current Qwen3 4B path is the baseline.

7. Do not replace the server-owned Focus Together SSE contract with browser-only
   state or polling.

8. Do not add embeddings/vector search before defining per-user isolation,
   deletion, rebuild, encryption, and memory/disk budgets.

9. Do not introduce a frontend framework only for visual polish. The current
   Jinja + vanilla JS architecture can be modularized incrementally.

10. Do not expose chain-of-thought, private prompts, memory-ranking internals, or
    Companion Brain JSON as companion text.

SUCCESS MEASURES
================

Track outcomes rather than feature count:

- Zero lost or duplicate chat turns in interruption and concurrency tests.
- Zero duplicate scheduled check-ins across multiple workers.
- Successful restore drills and measured RTO/RPO.
- p95 chat queue wait, first-token time, and TTS-start time within defined budgets.
- Error and fallback rates categorized without collecting private content.
- Reduced repeated/regenerated responses and fewer "forgot context" reports.
- Accessibility completion rate for keyboard and screen-reader journeys.
- Retention improvement for users who opt into weekly review or goal steps.
- Correct account deletion and export coverage verified automatically.
- No claims of production payment, audio playback, camera privacy, or real-time
  synchronization based only on unit tests.
